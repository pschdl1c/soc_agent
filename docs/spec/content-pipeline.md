# Конвейер детект-контента

**Модули:** `scripts/content_lib.py`, `scripts/deploy_content.py`, `scripts/test_content.py`
**Назначение:** доставка детект-контента из git в SIEM и проверка его синтетическими фикстурами.

Это спецификация **инструментов**. Соглашения по написанию самого контента (именование, авторство,
адаптация SigmaHQ, guard-блоки, границы доменов) — `CLAUDE.md` §9.

## Область ответственности

- Источник правды по контенту — git (`artifacts/content/`); в SIEM контент попадает ТОЛЬКО через
  `deploy_content.py`.
- Деплой идемпотентен: повторный запуск на совпадающем состоянии ничего не меняет.
- Проверка контента — прогон фикстур через настоящий потоковый ingest живого экземпляра, без
  обращения к внутренним API приложения.
- Скрипты не импортируют `app.*` и работают через обычный HTTP API SIEM. Зависимости — stdlib и
  PyYAML (уже зависимость проекта).

Правка контента через UI-редактор — песочница: следующий деплой её перезапишет.

## Раскладка контента

```
artifacts/content/
  value_lists/<name>.yml        # {name, description, values}
  <domain>/rules/*.yml          # по одному базовому Sigma-правилу на файл
  <domain>/correlations/*.yml   # корреляции: агрегаторы, промежуточные звенья, сценарии SCE_
  <domain>/tests/*.yml          # фикстуры для test_content.py
  telemetry/                    # конфиг Sysmon стенда и схема полей событий; в SIEM НЕ грузятся
```

**Имя каталога домена = имя custom-рулсета в SIEM.** Каталоги `value_lists` и `telemetry`
доменами не считаются (`NON_DOMAIN_DIRS`), как и имена, начинающиеся с `.` или `_`.

## `content_lib.py` — общий слой

### `Api`

Тонкий клиент HTTP API поверх `urllib` (таймаут по умолчанию 120 с). `request(method, path, *,
params, body, raw, headers)` сериализует `body` в JSON, `raw` отправляет как есть (нужно для
NDJSON в `/ingest/stream`). Ошибка HTTP → `ApiError(status, detail, method, path)`.

### `ContentRule` / `Content`

`ContentRule` — один файл правила: `domain`, `path`, `kind` (`"base"` | `"correlation"`), `text`
(сырой YAML, он и уходит в API), `doc` (разобранный YAML). Свойства: `id`, `title`, `refs`
(`correlation.rules` — ссылки на другие правила).

`Content` — `value_lists` + `rules`; свойство `domains` — отсортированный список доменов.

### `load_content(content_dir=CONTENT_DIR, domains=None) -> Content`

Читает раскладку целиком и **проверяет инварианты, прежде чем что-либо уйдёт на сервер**:

| Проверка | Нарушение |
|---|---|
| У value list есть `name` | `ValueError` |
| Ни одно значение списка не имеет пробелов по краям | `ValueError` со списком значений |
| У правила есть `title` и `id` | `ValueError` |
| Наличие блока `correlation:` соответствует каталогу (`rules/` vs `correlations/`) | `ValueError` |

Проверка краевых пробелов — не придирка: сервер обрезает пробелы по краям значений
(`app/rules/value_lists.py`), а у Sigma-значений вроде `' -nop '` или `'cmd '` пробел значим.
После обрезки правило молча расширяется, поэтому такие перечни обязаны оставаться inline.

### `topo_correlations(rules) -> list[ContentRule]`

Корреляции в топологическом порядке по `correlation.rules`: правило, на которое ссылаются,
деплоится раньше ссылающегося. Нужно потому, что сервер проверяет разрешимость ссылок **на
сохранении** (`docs/spec/rules-catalog.md`), и обратный порядок дал бы 400.

### `custom_rulesets_by_name(api)` / `ruleset_rule_ids(api, ruleset_path)`

`{имя рулсета: логический путь}` по `GET /rulesets` и `{rule_id: строка списка}` по
`GET /rulesets/rules` — обе нужны деплою, чтобы отличить создание от обновления и найти переезды.

## `deploy_content.py` — доставка в SIEM

```
uv run python scripts/deploy_content.py                       # всё, в http://localhost:8000
uv run python scripts/deploy_content.py http://localhost:8001 --domain auth --prune
```

| Аргумент | Смысл |
|---|---|
| `url` (позиционный) | адрес SIEM, по умолчанию `http://localhost:8000` |
| `--content` | другой каталог контента |
| `--domain` | только эти домены (можно повторять) |
| `--prune` | удалить из SIEM то, чего нет в git (см. ниже) |
| `--no-main` | не включать рулсеты доменов в основной рулсет |

### Порядок шагов

Каждый шаг идемпотентен.

1. **Value lists** — `GET /value-lists/{name}`; нет → `POST /value-lists`, есть и отличается →
   `PUT`. `PUT` сразу пересобирает зависимые правила, счётчики пересобранного и ошибок печатаются.
2. **Базовые правила ВСЕХ доменов** — `POST /rules/custom` (нового) или `PUT /rules/custom/{id}`
   (если текст отличается). Рулсет домена создаётся первым `POST` через `new_ruleset_name` = имя
   каталога.
3. **Корреляции** — в порядке `topo_correlations`. Все базовые правила уже на сервере, поэтому
   межрулсетные ссылки разрешаются.
4. **`--prune`** — сначала корреляции, потом базовые правила, которых нет в git; затем value lists
   контента, которых нет в git.
5. **main** — рулсеты доменов включаются в основной рулсет целиком (`POST /main-ruleset/rulesets`),
   если не задан `--no-main`.

Правило, переехавшее в другой домен (тот же `id`, другой рулсет), удаляется из старого рулсета и
создаётся в новом.

### Границы `--prune`

Value lists удаляются **только в пространстве имён контента**: префиксы вычисляются из имён самих
списков в git (`cred_`, `exec_`, `common_`…), и список с другим именем, заведённый руками в UI, не
трогается. Список, на который ещё ссылается правило, отдаёт 409 и пропускается.

### Запуск без Python на хосте

`scripts/deploy_content.ps1` / `scripts/deploy_content.sh` запускают тот же скрипт в одноразовом
контейнере из образа `soc_agent:latest` (репозиторий смонтирован read-only, `localhost` в адресе
подменяется на `host.docker.internal`). Своей логики не несут.

## `test_content.py` — прогон фикстур

```
uv run python scripts/test_content.py http://localhost:8001 [--domain auth] [--scenario SCE_Auth_BruteForce] [--coverage]
```

Контент должен быть уже задеплоен и включён в основной рулсет. Гонять следует на **изолированном
экземпляре** — иначе прогон смешается с рабочими данными:

```
SIEM_DB_PATH=<temp>/siem-content.db
SIEM_CUSTOM_RULESETS_DIR=<temp>/content-rulesets
SIEM_VALUE_LISTS_DIR=<temp>/content-lists
uv run uvicorn app.main:app --port 8001
```

### Формат фикстуры

Файл `<domain>/tests/<SCE_имя>.yml`:

```yaml
scenario: SCE_Auth_BruteForce
cases:
  - name: positive
    expect_incidents: [auth_bruteforce]   # ТОЧНЫЙ набор incident_type этого кейса
    events:
      - at: 0          # смещение первого события, секунды (дефолт 0)
        repeat: 20     # сколько раз повторить (дефолт 1)
        step: 3        # шаг между повторами, секунды (дефолт 1)
        phase: 1       # фаза отправки (дефолт 1): фаза N+1 уходит после флаша фазы N
        vary:          # значение поля на i-м повторе - options[i % len(options)]
          TargetUserName: [admin, backup]
        event: {EventID: 4625, Channel: Security, IpAddress: 203.0.113.7}
lab:                   # команды эмуляции на стенде; скрипт их НЕ выполняет
  - '...'
```

Подстановки в строковых значениях события: `${host}`, `${i}` (номер повтора), `${guidN}`
(стабильный в пределах кейса GUID вида `{XXXXXXXX-…}`), `${rand}` (случайный хвост кейса).

### Как строится событие

1. Поля `vary` подставляются по номеру повтора, затем раскрываются `${…}`.
2. **Поля дополняются реальным набором стенда** по ключу `<Channel>|<EventID>` из
   `telemetry/event_fields_manual.json` и `telemetry/event_fields.json` (второй читается позже и
   при совпадении ключа побеждает — это выгрузка со стенда, первый описывает события, которых на
   стенде ещё нет). Недостающие поля получают значение `"-"` — так пустые поля пишет сам Sysmon;
   пустую строку Zircolite при flatten выбросил бы вместе с полем.
3. `Computer` проставляется хостом кейса, если не задан явно.
4. `TimeCreated` — `%Y-%m-%d %H:%M:%S +0000`, `EventTime` — ISO с микросекундами и `Z`.

Пункт 2 существует, потому что NULL и реальное значение ведут себя в SQL по-разному: правило
досоздаёт недостающие колонки (`docs/spec/detection-engine.md`), но `NOT (ParentImage LIKE …)` на
NULL — ложь, то есть фильтр по отсутствующему полю гасит правило. На живом потоке у Sysmon 1
всегда есть `ParentImage`/`User`/…, и синтетика без них проверяла бы не то, что придёт с
форвардера. Схема обновляется `scripts/export_event_fields.py` (выгрузка **сливается**, а не
перезаписывается — скрипт видит только события текущей БД).

### Изоляция и синхронизация

- Каждый кейс получает **свой временный источник** (`ct-<run>-<n>`) и свой случайный хост
  `CT-<rand>` — инциденты разных кейсов не смешиваются, потому что `incidents.dedup_key` включает
  `source_batch` (`docs/spec/incidents.md`).
- База времени — `now − 30 минут`, наивный UTC.
- События отправляются в `/ingest/stream` пачками по 400, NDJSON, с токеном источника кейса.
- Фазы отправляются последовательно: следующая уходит только после полного флаша предыдущей. Это
  и есть способ разнести события по разным флашам ingest-воркера.
- **Ожидание флаша — по маркерным событиям служебного источника**, а не по `queue_size == 0`:
  нулевая очередь значит лишь «воркер забрал события», а не «флаш закончен». Воркер обрабатывает
  флаши последовательно, поэтому появление в БД ВТОРОГО маркера, отправленного после записи
  первого, гарантирует, что флаш с событиями кейсов завершён целиком — включая корреляции.
  Таймаут одного маркера — 5 минут.
- После прогона источники и их данные удаляются (`DELETE /batches/{name}` + `DELETE
  /sources/{id}`), если не задан `--keep`.

### Проверка и коды выхода

Сверяется **точный набор** `incident_type` кейса: лишний инцидент — такой же FAIL, как
недостающий (так ловятся непреднамеренные пересечения сценариев). При FAIL печатаются ожидаемые и
полученные типы, названия сработавших correlation-правил и набор алертов кейса.

`--coverage` (только на полном прогоне, без `--domain`/`--scenario`) дополнительно печатает
правила контента, не сработавшие ни в одном кейсе: базовые — по алертам, инцидентные корреляции —
по инцидентам. **Тихие звенья** (`level: informational` без блока `incident`) через API не
наблюдаемы и из учёта исключены — их покрытие косвенное, через взведённые ими сценарии.

| Код выхода | Значение |
|---|---|
| `0` | все кейсы PASS, непокрытых правил нет |
| `1` | есть FAIL либо ошибка API/синхронизации |
| `2` | все кейсы PASS, но есть непокрытые правила |

## Инструменты автора контента

`scripts/content/` — не часть деплоя:

- `sigma_find.py` — поиск кандидатов в клоне SigmaHQ (`--sigma-repo` / `SIGMA_REPO`): по EventID,
  категории, тегу, подстроке; уже адаптированные помечены `*`.
- `adapt_sigma.py` — черновик адаптации правила SigmaHQ по соглашениям §9: guard, без
  `Provider_Name`, новый UUID + `related: derived`, авторство, вынос перечислений в value list.
- `new_correlation.py` — заготовка correlation-файла в стиле контента (сохраняет `id`
  существующего).

## Зависимости

- Импортируют: stdlib (`argparse`, `json`, `urllib`, `pathlib`, `datetime`, `uuid`, `re`, `time`),
  `yaml`. `app.*` — **нет**, взаимодействие только через HTTP API.
- Смежные спецификации: `docs/spec/http-api.md` (используемые ручки),
  `docs/spec/rules-catalog.md` (валидация правил на сохранении),
  `docs/spec/incidents.md` (`dedup_key`, привязка member-алертов),
  `docs/spec/detection-engine.md` (досоздание колонок и семантика NULL).
