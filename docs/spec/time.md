# Каноническая форма метки времени

**Модуль:** `app/timeutil.py`
**Назначение:** привести метку времени события к ОДНОЙ форме, в которой её можно сравнивать
строкой — на записи в БД и на разборе границ диапазона из запроса.

## Область ответственности

- `normalize_event_time(value)` — каноническая форма значения метки времени.
- `normalize_time_bound(value, upper=False)` — та же форма для границы диапазона, с
  включающей семантикой верхней границы.
- Никаких импортов из `app` (лист-модуль, как `app/timespan.py`): модуль используют и
  `app/store.py`, и `app/detection/correlation.py`, между которыми не должно быть завязки.

## Каноническая форма

`"YYYY-MM-DDTHH:MM:SS[.ffffff]"` — наивный (без `tzinfo`) ISO по UTC. Тот же формат, что у
`alerts.created_at` (`models.utcnow_naive`) и у границ из UI (`timeParams()` в `index.html` —
специально без `Z`/offset). Лексикографическое сравнение такой строки совпадает с
хронологическим.

## `normalize_event_time(value: str | None) -> str | None`

| Вход | Выход |
|---|---|
| `None` | `None` |
| `""` / только пробелы | вход без изменений |
| `"2026-09-05 21:01:30.113"` | `"2026-09-05T21:01:30.113000"` |
| `"2026-09-05T18:00:00Z"` | `"2026-09-05T18:00:00"` |
| `"2026-09-05T21:00:00+03:00"` | `"2026-09-05T18:00:00"` (перевод в UTC) |
| нераспознанный формат | `value.replace(" ", "T").replace("Z", "")` |

Алгоритм: `datetime.fromisoformat(raw.replace(" ", "T"))`; aware-значение → `astimezone(utc)` +
снятие `tzinfo`; naive считается УЖЕ UTC (зоны в метке нет и взять её неоткуда). Разбор,
завершившийся `ValueError`, откатывается на прежнее однострочное правило — неизвестная метка
времени не повод потерять событие на ingest.

## `normalize_time_bound(value: str | None, upper: bool = False) -> str | None`

Приводит границу диапазона к канонической форме. Пустая/отсутствующая граница → `None` (фильтр
не накладывается).

`upper=True` добавляет хвост-сентинель `chr(0xFFFF)`: верхняя граница включает всё, что её
продолжает. `time_to = "2026-09-05T21:01:30"` накрывает `"2026-09-05T21:01:30.113000"` и при
этом не захватывает `"2026-09-05T21:01:31"` — в UTF-8 `U+FFFF` (`EF BF BF`) больше любого
ASCII-байта, а канонические метки состоят только из ASCII. Нижней границе сентинель не нужен
и вреден: он отрезал бы события той же секунды с дробной частью.

## Где применяется

| Точка | Что делает |
|---|---|
| `store.store_events` | `events.event_time` и `rule_hits.event_time` пишутся ОДНИМ каноническим значением |
| `store._events_where` | границы `time_from`/`time_to` → `normalize_time_bound`, сравнение с голой колонкой |
| `store._backfill_event_time` | разовая канонизация строк, записанных до введения формы (отметка `schema_meta.event_time_canonical`) |
| `correlation.evaluate_batch` | метка нового попадания при расчёте окна — та же форма, что в леджере |

## Инварианты

- Колонка `events.event_time` и колонка `rule_hits.event_time` всегда в одной форме: они
  пишутся одним и тем же значением в одной операции.
- SQL сравнивает `event_time` НАПРЯМУЮ, без обёртки `replace(...)` — иначе планировщик не
  использует `idx_events_time` (индекс на колонке не работает для выражения от неё).
- Сырое значение источника не теряется: оно остаётся в `events.raw_json`.
