# Счётчики изменений для автообновления UI

Компонент: `app/updates.py` + эндпоинт `GET /updates` (`app/main.py`).

## Область ответственности

Отвечает на один вопрос открытой страницы UI: «изменились ли списки Алертов/Инцидентов с
момента, когда я их последний раз показывал». Только это — данными не владеет, в БД не ходит,
ничего не рассылает (push-транспорта нет, клиент опрашивает сам).

Не отвечает за: содержимое списков (`/alerts`, `/incidents`), живость сервиса (`/health`),
события (вкладка «События» автообновление не использует).

## Модель данных

Состояние — в памяти процесса, две пары счётчиков на канал (`CHANNELS = ("alerts",
"incidents")`) плюс идентификатор запуска:

| Поле | Тип | Смысл |
|---|---|---|
| `epoch` | `str` (16 hex) | Идентификатор запуска процесса, выдаётся при импорте модуля |
| `<channel>.version` | `int` | Монотонный счётчик ЛЮБОГО изменения канала |
| `<channel>.created` | `int` | Сколько строк канала реально СОЗДАНО с момента запуска |

Два счётчика, а не один, потому что «список изменился» и «появились новые строки» — разные
события. Повторное срабатывание правила не создаёт алерт, а инкрементит `event_count`
существующей строки (дедуп по `dedup_key`, см. `docs/spec/normalization.md`); вердикт
расследования меняет колонку `investigation_status` в списке инцидентов; `DELETE /batches/{...}`
удаляет строки. Всё это двигает `version` и не двигает `created` — UI перечитывает список, но
не пишет «N новых».

`epoch` нужен, потому что счётчики не персистятся: после рестарта они начинаются с нуля, и
клиент со снимком `version=42` без сравнения epoch молча не заметил бы, что сервер уехал на
`version=1`.

## API

### `bump(channel: str, created: int = 0) -> None`

`version += 1` всегда, `created += created` при ненулевом аргументе. Потокобезопасен (лок):
зовётся и из HTTP-обработчиков, и из фонового потока `IngestWorker`. Неизвестный `channel`
игнорируется молча — счётчик вспомогательный, ронять из-за него запись алерта нечего.

### `snapshot() -> dict`

`{"epoch": str, "alerts": {"version": int, "created": int}, "incidents": {...}}`. Возвращает
копии словарей — правка результата не протекает в состояние модуля.

### `_reset() -> None`

Тест-хук: обнуляет счётчики и выдаёт новый `epoch`.

## Точки вызова `bump`

| Место | Канал | `created` |
|---|---|---|
| `main.py:_process_batch`, после `store.upsert_alerts` (если были алерты) | `alerts` | число `dedup_key`, которых не было в БД до записи |
| `detection/correlation.py:evaluate_batch`, после `upsert_correlation_alerts` | `alerts` | `0` |
| `detection/correlation.py:evaluate_batch`, после `upsert_incidents` | `incidents` | число записей с `was_new=True` |
| `incidents.py:run_pending`, если обработана хотя бы одна строка | `incidents` | `0` |
| `main.py: PATCH /incidents/{id}/status` | `incidents` | `0` |
| `main.py: DELETE /batches/{source_batch}` | `alerts` + `incidents` | `0` |

Бампится в точках ЗАПИСИ, а не в одной точке оркестрации: в `alerts`/`incidents` пишут три
модуля, и собрать это в одном месте можно было бы только протаскиванием счётчиков через
возвращаемые значения.

`created` для обычных алертов считается отдельным `store.get_alert_ids_by_dedup_keys(...)` ДО
`upsert_alerts`: та возвращает число ОБРАБОТАННЫХ строк (новые от дедуплицированных по нему не
отличить), а менять её контракт нельзя — то же число уходит в `IngestResponse.alerts_created`.
Один запрос по индексу `dedup_key` на батч, на фоне фиксированного оверхеда прогона движка
(~0.25 с) незаметен.

`created=0` для correlation-алертов — намеренно: `upsert_correlation_alerts` перезаписывает
строку на каждом flush, пока окно живо, и «N новых» росло бы на ровном месте.

## Эндпоинт

`GET /updates` → `snapshot()`. Полностью в памяти, без обращения к БД: ручку опрашивает каждая
открытая вкладка раз в несколько секунд, поэтому она обязана быть дешевле самого списка.
Отдельная от `/health` — разный ритм опроса (7 с против 20 с) и разная семантика (свежесть
данных против живости сервиса).

## Клиент (`app/static/index.html`)

`pollUpdates()` раз в `UPDATES_POLL_MS` (7000), только когда активна вкладка Алерты или
Инциденты и `document.hidden === false`; `visibilitychange` форсирует опрос при возврате.
Сравнивает ответ с `updatesSeen` (снимок, уже отражённый в показанном списке):

- `epoch` изменился → считаем, что данные могли уехать (`changed = true`);
- `version` не изменилась → выход;
- иначе `changed = true`, `created += max(0, new.created - seen.created)`.

Дальше: если `canAutoRefresh(channel)` — активная вкладка, первая страница пейджера, нет
выделенной строки (открытой карточки) — список перечитывается тихо; иначе показывается бейдж
`↑ N новых алертов` (или `↻ Данные обновились`, если `created` не рос), по клику —
`RELOAD_FNS[channel]()`.

`loadAlerts`/`loadIncidents` в начале зовут `resetUpdatesBaseline(channel)`: гасят бейдж и
берут точку отсчёта запросом к `/updates` — не «поверим следующему поллингу», иначе флаш
ingest между перезагрузкой списка и следующим тиком был бы молча принят за уже показанный.
Запрос идёт ДО запроса списка: так снимок заведомо не новее показанных данных, и в худшем
случае бейдж покажется лишний раз (ложное срабатывание безопаснее пропущенного).

## Ограничения

- **Один процесс.** Счётчики живут в памяти, поэтому схема верна для `uvicorn` без
  `--workers` (как в `Dockerfile`). При нескольких воркерах у каждого свой счётчик, и UI
  начнёт дёргать список на каждом поллинге, попадая то в один процесс, то в другой. Тогда
  состояние переезжает в общее место (БД / redis) — та же развилка, что и при переходе на SSE.
- **Не push.** Задержка до `UPDATES_POLL_MS`; SSE/WebSocket (Этап 2 дорожной карты) заменит
  только транспорт — счётчики и клиентская логика бейджа останутся теми же.
- **События не покрыты** намеренно: там фильтр/группировка/drill-in, автоперезагрузка сломала
  бы разбор в середине работы.
