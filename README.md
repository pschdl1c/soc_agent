# soc_agent

Лёгкий SIEM на Sigma-правилах (движок [Zircolite](https://github.com/wagga40/Zircolite)) с
веб-консолью аналитика и для AI-агента, который будет автоматически расследовать
алерты и выносить вердикт (`true positive` / `false positive` / `needs review`).

Полный технический гайд по архитектуре, модулям и соглашениям — в [`CLAUDE.md`](./CLAUDE.md).
Этот README — практическое введение: что это, как запустить, как пользоваться.

## Что делает проект

1. Принимает логи (EVTX / Sysmon / auditd-подобный JSON и т.п.) — файлом, порцией JSON-событий
   или потоком с форвардера (Winlogbeat/NXLog/самописный).
2. Прогоняет их через **Sigma-правила** движком **Zircolite** и получает сработавшие детекты.
3. Нормализует детекты в **алерты** (с дедупликацией, MITRE-тегами, сэмплами событий) и хранит
   вместе со **всеми** событиями батча (не только сработавшими) — для ручного пивота и будущего
   RAG-агента.
4. Показывает всё это в веб-консоли: алерты, события с фильтром/группировкой, каталог
   Sigma-правил с собственным редактором правил.

AI-агент расследования — следующий этап (см. [дорожную карту](#дорожная-карта)), в текущем виде
не реализован.

## Статус

Работает полный пайплайн **ingest → Sigma-детект → нормализация → хранение → UI**, включая:
потоковый ingest с очередью и микро-батчингом, собственный каталог Sigma-правил (built-in +
именованные custom-рулсеты) со встроенным редактором, механизм «основного рулсета» (виртуальная
композиция правил из разных источников), фильтр/группировку событий на собственном мини-языке
запросов, реальные health-чеки. Подробный чеклист по этапам — в
[дорожной карте](#дорожная-карта) ниже (она же поддерживается в `CLAUDE.md` как источник истины).

## Установка

```powershell
git clone <repo-url> soc_agent
cd soc_agent

python -m venv .venv
.venv\Scripts\Activate.ps1

pip install -r requirements.txt
# для разработки/тестов:
pip install -r requirements-dev.txt
```

Также нужен клон **Zircolite** рядом (используется как библиотека, не как pip-пакет):

```powershell
git clone https://github.com/wagga40/Zircolite.git
```

Репозиторий должен лежать по пути `./Zircolite` относительно корня проекта — `app/engine.py`
подключает его через `sys.path`, а `app/main.py` использует `Zircolite/config/config.yaml` и
готовые скомпилированные рулсеты из `Zircolite/rules/*.json` (пути настраиваются через `.env`,
см. [Конфигурация](#конфигурация-env) ниже).

## Запуск

```powershell
.venv\Scripts\Activate.ps1
uvicorn app.main:app --reload --port 8000
# либо (host/port берутся из .env, см. ниже; --reload не подключается в этом варианте):
python -m app.main
```

- Веб-консоль: http://localhost:8000/
- Swagger (все ручки): http://localhost:8000/docs
- Health-check: http://localhost:8000/health (добавь `?detailed=true` для счётчиков строк/размера БД)

При старте `app/main.py` один раз компилирует дефолтный рулсет
(`Zircolite/rules/rules_windows_merged.json`) — это самая дорогая операция инициализации,
дальше используется кэш (см. [Производительность](#производительность-и-масштаб)).

## Конфигурация (.env)

Пути, хост/порт и параметры потокового ingest читаются из окружения (`app/config.py`, на
основе `python-dotenv`) — по умолчанию всё работает без единой переменной (значения выводятся
относительно корня проекта). Чтобы переопределить — скопируй шаблон и раскомментируй нужное:

```powershell
copy .env.example .env
```

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `SIEM_DB_PATH` | `<корень>/siem.db` | Путь к файлу SQLite |
| `SIEM_ZIRCOLITE_CONFIG_PATH` | `<корень>/Zircolite/config/config.yaml` | Конфиг движка Zircolite |
| `SIEM_DEFAULT_RULESET_PATH` | `<корень>/Zircolite/rules/rules_windows_merged.json` | Рулсет по умолчанию для `/ingest/file`·`/ingest/upload` без явного `ruleset` |
| `SIEM_UPLOADS_DIR` | `<корень>/data/uploads` | Куда сохраняются файлы, загруженные через UI |
| `SIEM_HOST` / `SIEM_PORT` | `127.0.0.1` / `8000` | Используются только при `python -m app.main`; для `uvicorn app.main:app` хост/порт задаются флагами CLI |
| `SIEM_INGEST_BATCH_SIZE` / `SIEM_INGEST_FLUSH_INTERVAL` | `500` / `5.0` | Политика микро-батчинга потокового ingest (`app/ingest_queue.py`) |

Явно выставленная переменная окружения всегда имеет приоритет над значением из `.env`.

## Docker

```powershell
docker compose up -d --build
```

- Веб-консоль/Swagger/health — те же адреса, что и без Docker: http://localhost:8000/,
  http://localhost:8000/docs, http://localhost:8000/health.
- `docker-compose.yml` пробрасывает порт 8000 и монтирует runtime-данные:
  - `siem.db` — **именованный volume** (`siem_db`), НЕ bind-mount. На Docker Desktop с
    WSL2-бэкендом (Windows) bind-mount на путь хоста (`D:\...`) означает, что каждое
    обращение SQLite идёт через границу Windows↔WSL2 - при частых мелких random-read
    (`GROUP BY`/фильтр с `json_extract` по каждой строке `events`) это даёт замеренную
    просадку на порядок (~3.3с против ~0.25с на идентичном файле/запросе — bind-mount vs
    native). Именованный volume физически живёт на диске самой Docker VM (WSL2-диск), без
    пересечения границы - скорость как без Docker вовсе. Обратная сторона - siem.db
    больше не открыть напрямую из Windows (Проводник/DB Browser); посмотреть содержимое -
    `docker compose exec soc_agent sqlite3 /app/db/siem.db` или скопировать наружу
    (`docker cp soc_agent-soc_agent-1:/app/db/siem.db .`).
  - `./data/uploads` и `./data/custom_rulesets` (bind-mount, монтируются в `/app/data/uploads`
    и `/app/data/custom_rulesets`) - те же дефолтные пути, что и при запуске **без** Docker
    (`app/config.py:UPLOADS_DIR`, `app/rules_catalog.py:CUSTOM_ROOT` резолвят их
    относительно корня проекта в `./data/uploads`/`./data/custom_rulesets` в обоих
    случаях) - один и тот же файл на диске, что бы вы ни выбрали для запуска, без ручной
    синхронизации между режимами. Эти два - не на горячем пути (редкие целые файлы, не
    тысячи мелких обращений на HTTP-запрос), поэтому bind-mount тут не мешает и даёт
    видимость файлов с хоста.

  Все три переживают `docker compose down`/пересборку образа. `./data/uploads`·
  `./data/custom_rulesets` удаляются вручную (`rm -rf data`); `siem_db` - `docker compose
  down -v` или `docker volume rm soc_agent_siem_db`.
- `Dockerfile` — multi-stage: в builder-слое клонируется `Zircolite`
  (движок детекта — внешний репозиторий, импортируется как библиотека, не pip-пакет, см.
  [Стек](#стек)) на зафиксированном теге (`ZIRCOLITE_REF`, по умолчанию `v3.7.6` — версия,
  реально используемая при разработке; поменять — `docker compose build --build-arg
  ZIRCOLITE_REF=v3.x.x`), в runtime-слое — только venv и код приложения, без git/компиляторов,
  под непривилегированным пользователем.
- Конфигурация — те же переменные, что в [.env](#конфигурация-env), заданы в `environment:`
  блоке `docker-compose.yml` (`SIEM_HOST=0.0.0.0` обязательно — иначе сервер слушает только
  локалхост контейнера и порт наружу не пробросится; остальные — по необходимости).
- Готовый образ без compose: `docker build -t soc_agent . && docker run -p 8000:8000
  -v siem_db:/app/db -v "${PWD}/data/uploads:/app/data/uploads" -v
  "${PWD}/data/custom_rulesets:/app/data/custom_rulesets" -e SIEM_HOST=0.0.0.0 soc_agent`.
- ⚠️ Как и без Docker — сервис не имеет аутентификации (см.
  [Известные ограничения](#известные-ограничения)); пробрасывать порт 8000 наружу localhost
  можно только за доверенным периметром/reverse-proxy с своей авторизацией.

## Тесты

```powershell
pip install -r requirements-dev.txt
pytest
```

Мини-набор в `tests/` (pytest, конфигурация — `pytest.ini`): unit-тесты `engine.py` (кэш
скомпилированного рулсета, матчинг правил), `normalize.py` (группировка алертов по хост+источник,
dedup-ключ, entities) и `store.py` (upsert/дедуп, фильтр/группировка событий, удаление батча,
health), плюс один e2e-тест на весь пайплайн ingest → детект → alert/event storage. Все тесты
работают на временных `tmp_path`-файлах (свой `siem.db` и свой ruleset на тест) — реальная
`siem.db` и дефолтный рулсет проекта не затрагиваются. Тестам, использующим движок, нужен
склонированный `./Zircolite` (см. [Установку](#установка)) — при его отсутствии они
автоматически skip-аются, а не падают.

## Быстрый старт: первый прогон логов

Тестовые датасеты атак лежат в `artifacts/Security-Datasets/` (клон
[OTRF Security-Datasets](https://github.com/OTRF/Security-Datasets)) и в `uploads/`.

**Вариант A — через веб-консоль:** вкладка «Источник данных» → загрузить файл (EVTX/JSON) →
выбрать рулсет (или оставить дефолтный) → посмотреть результат во вкладках «Алерты»/«События».

**Вариант B — через API:**

```bash
curl -X POST "http://localhost:8000/ingest/upload" \
  -F "file=@artifacts/Security-Datasets/datasets/.../some.evtx" \
  -F "ruleset=main"
```

**Вариант C — синтетический форвардер** (проверка потокового ingest, без реальных логов):

```powershell
python scripts/fake_forwarder.py burst   # много событий разом - проверка size-trigger
python scripts/fake_forwarder.py drip    # медленно и долго - проверка time-trigger
```

Скрипт печатает состояние очереди из `/health?detailed=true` по ходу отправки.

## Архитектура и поток данных

```
        файл логов / порция событий / поток с форвардера
                   │
        POST /ingest/{file|events|upload|stream}
                   │
                   ▼
        ┌──────────────────────┐
        │  ZircoliteEngine      │  app/engine.py
        │  • ruleset кэшируется  │  Sigma-правила компилируются в SQL ОДИН раз при старте
        │    один раз (дорого)   │  (RulesetHandler), переиспользуются на каждый батч
        │  • на батч — новый     │  ZircoliteCore с in-memory SQLite
        │    ZircoliteCore       │
        └──────────┬───────────┘
                   │ raw_results (сработавшие правила + row_id),
                   │ all_events (ВСЕ события после flatten)
                   ▼
        ┌──────────────────────┐        ┌──────────────────────┐
        │  normalize.py         │        │  store.py (SQLite)    │
        │  raw_results → Alert  │───────▶│  таблица alerts       │  (дедуп по dedup_key)
        │  (группировка по хосту,│        │  таблица events       │  (все события + метки)
        │   источнику, entities) │        └──────────────────────┘
        └──────────────────────┘                   │
                                                    ▼
                             GET /alerts · /events · /batches → UI (index.html)
```

Потоковый ingest (`/ingest/stream`) не бьёт движок отдельно на каждый источник: события из
разных источников копятся в одной очереди (`app/ingest_queue.py`) и на флаше прогоняются через
Zircolite **одним вызовом** (у движка фиксированный оверхед на батч, ~0.25с на ~4300 правилах,
почти не зависящий от числа событий) — источник каждого события временно кодируется прямо в
событии и снимается после прогона, до сохранения в БД. Подробности — в `CLAUDE.md` (`app/fields.py`
→ `INGEST_SOURCE_FIELD`, `app/ingest_queue.py`).

Подробное описание каждого модуля `app/*.py` — в таблице «Ключевые модули» в `CLAUDE.md`.

├── scripts/                вспомогательные скрипты для ручного тестирования

## Веб-консоль

Одностраничное приложение (`app/static/index.html`) с 4-мя основными вкладками:

- **Источник данных** — загрузка логов (файл с диска сервера или через браузер), таблица
  загруженных источников (`/batches`) с возможностью удалить источник целиком (события + алерты).
- **Алерты** — список алертов с фильтрами (источник, статус, severity, временной интервал),
  серверной сортировкой, карточкой алерта (правило, MITRE, сущности, сэмплы событий, смена статуса).
- **События** — таблица всех событий батча (не только сработавших), с:
  - **фильтром** на собственном мини-языке (в духе MaxPatrol query bar): `поле оператор значение`,
    `and`/`or`/`not` с приоритетом как в SQL, произвольная вложенность через скобки, операторы
    `=`/`!=`/`>`/`<`/`>=`/`<=`/`contains`/`in(...)`/`is null`/`is not null`, спецполя `rule` и
    `is_matched` для результата детекта;
  - **группировкой** — панель агрегаторов слева, клик = drill-in в события группы;
  - настраиваемыми колонками (перетаскивание порядка, resize по ширине, именованные fieldset-ы);
  - временными пресетами (15м/1ч/24ч/7д + произвольный интервал).
- **Sigma-правила** — просмотр built-in и custom-рулсетов, поиск, фильтр по `status`/`level`,
  полноэкранный редактор своих правил с живой подсветкой YAML-синтаксиса и панелью для сверки с
  уже существующими правилами, управление «основным рулсетом» (какие правила реально
  участвуют в детекте потокового ingest).

Светофор статуса сервиса в шапке — реальная проверка `/health` (БД/Zircolite/очередь ingest),
опрашивается раз в 20с.

## API

Полный список параметров и семантики — в CLAUDE.md, раздел «API (обзор)». Кратко:

| Метод | Путь | Назначение |
|-------|------|-----------|
| POST | `/ingest/stream` | Потоковый приём с форвардеров (NDJSON/JSON-массив), 202 → очередь → микро-батч |
| POST | `/ingest/file` | Прогон файла на диске сервера |
| POST | `/ingest/events` | Синхронный прогон порции сырых событий из тела запроса |
| POST | `/ingest/upload` | Загрузка файла из браузера (multipart) |
| GET/DELETE | `/batches` | Сводка по источникам / удаление источника целиком |
| GET/PATCH | `/alerts` | Список, карточка, смена статуса алерта |
| GET | `/events`, `/events/group` | Список/карточка событий, агрегаторы для группировки |
| GET | `/rulesets`, `/rulesets/rules`, `/rulesets/rule` | Каталог рулсетов и правил |
| POST/PUT/DELETE | `/rules/custom` | Создание/редактирование/удаление своих правил |
| POST | `/rulesets/upload` | Загрузка сырого Sigma YAML (рулсет или отдельные правила) |
| POST | `/main-ruleset/rules`, `/main-ruleset/rulesets` | Управление составом основного рулсета |
| GET | `/health` | Health-check (`?detailed=true` — счётчики) |

Swagger UI со всеми схемами запросов/ответов — http://localhost:8000/docs после запуска.

## Потоковый ingest с форвардеров

`POST /ingest/stream` принимает NDJSON или JSON-массив событий (`?source=<имя>`), кладёт их в
очередь и сразу отвечает `202 Accepted` — фоновый воркер (`app/ingest_queue.py`) флашит буфер по
правилу «N событий ИЛИ T секунд» (`SIEM_INGEST_BATCH_SIZE`=500, `SIEM_INGEST_FLUSH_INTERVAL`=5.0,
настраиваются переменными окружения). Рулсет для этого пути не выбирается per-request — всегда
«основной рулсет» (`app/main_ruleset.py`).

Протокол и примеры конфигурации форвардеров — в [`docs/forwarder.md`](./docs/forwarder.md).

## Sigma-правила и рулсеты

- **Built-in** рулсеты — уже скомпилированные `Zircolite/rules/*.json` (read-only), по умолчанию
  используется `rules_windows_merged.json`.
- **Custom-рулсеты** — любое число именованных наборов в `custom_rulesets/<id>/`: `meta.json` +
  сырой Sigma YAML на правило (source of truth) + кэш скомпилированных метаданных. Создаются и
  редактируются прямо из вкладки «Sigma-правила» (полноэкранный редактор с живой подсветкой) или
  загрузкой готового YAML-файла (в т.ч. multi-document).
- **Основной рулсет** (`main`) — виртуальная композиция: любые целиком добавленные рулсеты плюс
  точечные исключения/добавления отдельных правил. Это то, что реально гоняет потоковый ingest
  (`/ingest/stream`, `/ingest/events`) — по умолчанию у них нет выбора рулсета per-request.

## Хранилище данных

SQLite (`siem.db`), WAL-режим, две таблицы:

- **`alerts`** — нормализованные алерты. Дедуп по `dedup_key = sha256(rule_id:host:main_entity)[:16]`
  — повторное срабатывание инкрементит `event_count`, а не создаёт новый алерт.
- **`events`** — снимок всех событий батча (включая не вызвавшие ни одного правила), с флагом
  `is_matched` и списком `matched_rules` — нужны для ручного пивота и будущего RAG-агента.

Раздельные read/write SQLite-соединения (читатели не блокируют ingest-воркер и наоборот) плюс
expression-индекс на `EventID` для быстрой фильтрации/группировки по этому «горячему» полю —
подробности механизма и как безопасно добавить новое индексируемое поле — в CLAUDE.md, §8.

## Производительность и масштаб

- Компиляция Sigma-правил в SQL — самая дорогая операция, делается **один раз** при старте
  процесса (или при добавлении нового custom-правила/рулсета) и кэшируется по пути рулсета.
- Прогон движка на батч имеет фиксированный оверхед (~0.25с на ~4300 скомпилированных правилах),
  почти не зависящий от числа событий в батче — поэтому потоковый ingest **не** гоняет движок
  отдельно на каждый источник, а сливает буфер флаша в один прогон (см.
  [Архитектуру](#архитектура-и-поток-данных)).
- WAL-режим + раздельные read/write-соединения снимают конкуренцию за лок между аналитиком,
  листающим «События», и фоновым ingest-воркером.
- Expression-индекс на `EventID` (`idx_events_json_eventid` в `store.py`) — фильтр/группировка по
  этому полю не сканируют таблицу целиком.
- Параметр `limit` у `/events` жёстко ограничен диапазоном `1..500` (иначе `400`).

## Известные ограничения

- Тестов пока мало (мини-набор для этапа 0) — не покрыты `rules_catalog.py`/`main_ruleset.py`/`filter_lang.py`/HTTP-слой `main.py`.

- AI-агент расследования (главная цель проекта) пока не реализован — есть только данные и
  архитектура, готовые под него.
